
# Тестовое задание


## Как запустить
```
pip install -r requirements.txt && uvicorn main:app --host 0.0.0.0 --port 8000
```
Перед запуском убедитесь, что файл с каталогом находится в корневой директории. Если название каталога отлично от ```catalog_exel.csv```, необходимо прописать его название в ```.env```
  

## Какие решения принял и почему
Для подбора товара по запросу пользователя были выбраны  алгоритм ```TF-IDF``` и поиск по косинусному расстоянию с разбиением текста на символьные N-граммы.
### Почему
Это легковесное решение, которое идеально работает оффлайн, загружается за доли секунды и отлично справляется с опечатками и сленгом
### Компромиссы
Метрика косинусного сходства (confidence) может казаться математически низкой из-за штрафов за "лишние" слова в запросе, однако она отлично кластеризует нужные результаты. Границы отсечения ($T_{high} = 0.85$, $T_{low} = 0.30$) были выведены эмпирически на основе тестовой выборки для минимизации ложных срабатываний.

### Что попробовал (попробовал бы) и отбросил
* ***LLM / трасформеры*** - неоправданно тяжелое решение, требующее лишних ресурсов
* ***Тяжелые NLP-библиотеки (SpaCy, pymorphy3)*** - лемматизация будет работать хуже из-за игнорирования численных значений (размеров)

### Что бы довел до продакшена
* ***NER*** - извлечение сущностей и размеров для более точного фильтра
* ***Работа с опечатками*** -  интеграция легковесного спеллчекера алгоритма Норвига повысила бы итоговый score для сильно искаженных слов

## Масштаб
Если система вырастет до 2 миллионов товаров в 50 магазинах, текущий подход с перемножением матриц в оперативной памяти $O(N \times V)$ станет узким местом. Изменения в архитектуре потребуют следующих шагов:

1.  **Хранение данных и Multi-tenancy:**
    
    Каталог переезжает в PostgreSQL. Для разделения 50 магазинов вводится поле `tenant_id` (или `store_id`), по которому настраивается партицирование таблиц (Table Partitioning). Поиск всегда должен жестко фильтроваться по `tenant_id` на уровне запроса.
    
2.  **Оптимизация поиска (PostgreSQL + pg_trgm):**
    
    Логику N-грамм из памяти можно перенести на уровень базы данных с помощью расширения `pg_trgm`. Создание GIN-индексов по текстовому полю позволит базе данных самой крайне быстро находить нечеткие совпадения и опечатки без выгрузки миллионов строк в приложение.
    
3.  **Пайплайн на базе векторных баз данных (RAG подход):**
    
    При дальнейшем усложнении запросов классический поиск можно заменить на полноценную архитектуру Retrieval-Augmented Generation. Тексты товаров прогоняются через легковесную модель для получения эмбеддингов и сохраняются в векторную базу данных или в тот же PostgreSQL с расширением `pgvector`. Это обеспечит высокую скорость поиска и глубокое семантическое понимание запросов в масштабах миллионов записей.
